# Arduino setup tool design: beating SimHub's one-click firmware flow

## Executive summary

SimHub's Arduino experience works because it turns hardware assembly into a guided, generated-firmware flow:

1. Open **Arduino** in SimHub.
2. Click **Open arduino setup tool**.
3. Give the board a unique name.
4. Pick a board and enable one or more modules such as **RGB Leds**, **RGB Matrix**, **Screens**, **TM1638 / 7-seg**, **Gauges**, **Buttons**, **Encoders**, **ShakeIt motors**, or **Wind**.
5. Choose pins/options, pick the COM port, then click **Upload to arduino**.
6. SimHub generates the sketch, compiles/uploads it, reconnects, and the module appears in the relevant editor.

The UX win is the user's described happy path: **pick an 8x8 LED module -> pick its firmware -> it flashes -> it just works**.

Our app can exceed this by making the firmware step more explicit and less fragile:

- A searchable **module catalog** with photos, wiring, compatible boards, power warnings, and pin conflict checks.
- A one-click **Flash firmware for this module** wizard for each component in Hardware Hub.
- Precompiled `.hex`/`.bin` firmware where possible, generated by `arduino-cli` in CI/development.
- Bundled Windows `avrdude` for Uno/Nano/Mega/Leonardo/Pro Micro class boards, and `esptool` for ESP.
- Post-flash auto-detect via our companion v2 handshake: app sends `?`, firmware replies `K:<key>=<detail>` lines followed by `KEND`.
- Automatic Hardware Hub profile creation from detected capabilities, so users do not manually re-enter what firmware already knows.

## 1. SimHub's Arduino model

### Setup UX

SimHub's setup model is board-first and sketch-generation-first:

1. User opens the **Arduino Setup tool** from the Arduino section.
2. If Arduino IDE components are missing, SimHub prompts to download required Arduino components.
3. User enters a **unique Arduino name**. This is required for multi-Arduino support.
4. User enables the desired features/modules.
   - Example from SimHub docs: set TM1638 enabled modules to `2` when two TM1638 modules are wired.
   - SimHub warns that defaults can reuse pins because no single board can host every combination; users must ensure all used pins are unique.
5. User selects COM port and board.
6. User clicks **Upload to arduino**.
7. User optionally saves the setup profile for later changes.
8. SimHub then uses the module-specific editors: LED editor, matrix editor, display/alerts, gauge calibration, ShakeIt output configuration, input/action mapping.

Source: https://github.com/SHWotever/SimHub/wiki/Arduino--Setup

### Mental model

SimHub does not treat Arduino as one generic serial protocol. It treats it as a generated device firmware with selected compile-time capabilities:

- **Board**: Uno/Nano/Mega/Pro Micro/Leonardo.
- **Enabled modules**: RGB LEDs, matrix, OLED/LCD, 7-seg, gauges, inputs, motors, fans, custom protocol.
- **Pins/options**: pin numbers, count, chipset, color order, serpentine matrix, I2C address/library, button wiring mode, gamepad mode.
- **Generated firmware**: a sketch containing only selected modules/libraries so small AVR boards can fit memory constraints.
- **Runtime editors**: after flashing, SimHub's UI addresses the configured device by name/USB order and sends telemetry-specific output.

### The exact one-click module flow to match first

For an 8x8 LED matrix / iFlag, SimHub's practical flow is:

1. User wires a supported 8x8 module:
   - WS2812B matrix: `DIN -> D6`, `GND -> GND`, `VCC -> VIN` per SimHub's page.
   - SunFounder DM163 shield: plug shield into Uno/Leonardo.
   - SunFounder SH1.0-4P I2C RGB matrix: Uno-only per SimHub docs.
2. User opens the Arduino Setup tool.
3. User picks the board and COM port.
4. User enables the matching firmware module:
   - **DM163 Matrix**,
   - **SUNFOUNDER SH1.0-4P I2C RGB matrix**, or
   - **WS2812B Matrix**.
5. User sets matrix options such as serpentine layout and rotation where needed.
6. User uploads.
7. The matrix is then available in SimHub to show gears, flags, spotter, and custom animations.

Source: https://github.com/SHWotever/SimHub/wiki/Arduino-RGB-Matrix

### Multiple Arduino behavior

SimHub can aggregate several Arduinos as one logical device. In multi-USB mode, these features are addressable separately:

- 7-segment displays: TM1638, TM1637, MAX7219.
- 20x4 LCD.
- RGB LEDs and TM1638 LEDs.
- Motors.
- Custom protocol.

Other features can be replicated across boards, e.g. tach/boost/gear indicator. SimHub requires unique names and explicit scan/apply steps.

Source: https://github.com/SHWotever/SimHub/wiki/Arduino-Multiple-devices-support

### Custom protocol

SimHub also supports custom Arduino messages:

- App-side message formulas are built with NCalc.
- Messages are sent as strings, terminated by `\n`.
- Empty messages are not sent.
- Messages are sent only when their value changes.
- Custom protocol is available only in multiple USB mode so messages route to the intended Arduino.
- Arduino-side handler lives in `SHCustomProtocol.h`.

Source: https://github.com/SHWotever/SimHub/wiki/Custom-Arduino-Hardware-Support

## 3. Boards SimHub supports and upload mechanism

### SimHub-supported boards

SimHub's Arduino setup page recommends:

- Arduino Uno R3 or clone; **Uno R4 unsupported**.
- Arduino Nano v3 ATmega328 or clone; **ATmega168 Nano clones unsupported**.
- Arduino Mega 2560 or clone.
- Arduino Pro Micro **5V/16 MHz** or clone.
- Arduino Leonardo or clone.

It warns about fake CH340G chips, WAVGAT fake boards, missing Windows serial drivers, and the fact that gamepad features only work on Pro Micro/Leonardo/ATmega32U4 boards.

Source: https://github.com/SHWotever/SimHub/wiki/Arduino--Setup

### Practical flashing matrix for our app

SimHub's public wiki documents the setup/upload UX and supported boards, but not the exact command line. For our implementation, use standard Arduino bootloader upload conventions and precompiled artifacts.

| Board family | SimHub support | Bootloader / upload tool | Our flash command strategy | Notes |
|---|---:|---|---|---|
| Uno R3 / Nano v3 ATmega328P | Yes | Optiboot/STK500 over serial via `avrdude -c arduino` | `avrdude -c arduino -p atmega328p -P <port> -b 115200 -U flash:w:<hex>:i` | Nano clones may need old bootloader baud `57600`; expose an "Upload failed? Try old Nano bootloader" option. |
| Mega 2560 | Yes | STK500v2 via `avrdude -c wiring` | `avrdude -c wiring -p atmega2560 -P <port> -b 115200 -D -U flash:w:<hex>:i` | More flash/RAM; best AVR board for screens + many modules. |
| Leonardo | Yes | Caterina/avr109 with 1200 bps touch | Touch `<port>` at 1200 bps, wait for bootloader port, then `avrdude -c avr109 -p atmega32u4 -P <bootloaderPort> -b 57600 -D -U flash:w:<hex>:i` | Native USB HID; port changes during reset. |
| Pro Micro 5V/16 MHz | Yes | Caterina/avr109 with 1200 bps touch | Same as Leonardo, with board-specific reset/port detection and retry UX | Best for button boxes needing HID gamepad mode. |
| ESP8266 | Not in the older SimHub Arduino wiki pages reviewed, but our `shared/devices.ts` already models it | ROM bootloader via `esptool.py` / esptool-js | `esptool --chip esp8266 --port <port> --baud 921600 write_flash 0x00000 <bin>` | Add after AVR MVP; useful for Wi-Fi or LED-heavy modules. |
| ESP32 | Not in the older SimHub Arduino wiki pages reviewed, but our `shared/devices.ts` already models it | ROM bootloader via `esptool.py` / esptool-js | `esptool --chip esp32 --port <port> --baud 921600 write_flash 0x1000 <bootloader> 0x8000 <partitions> 0x10000 <app>` | Best for big RGB matrices/strips, but requires `.bin` bundle strategy. |

For the first Windows release, bundle `avrdude.exe`, `avrdude.conf`, and precompiled AVR `.hex` files. Use `arduino-cli` during development/CI to build those `.hex` files, not on the user's machine. Keep `arduino-cli` as an advanced fallback for custom pin/module combinations.

## 4. How our app should exceed SimHub

### Current app assets to build on

The app already has the right architecture for a better flow:

- `src/shared/devices.ts`
  - Board catalog: Pro Micro, Leonardo, Uno, Nano, Mega 2560, ESP32, ESP8266, generic.
  - Component model: `rgbStrip`, `rgbMatrix`, `screen`, `segDisplay`, `gauge`, `control`, `buzzer`, `startLed`.
  - Per-component pin roles, defaults, and Hardware Hub profile schema.
- `src/shared/companion.ts`
  - Companion protocol v1: OLED rows, bignum, rev percent, shift blink, mono 8x8, per-LED color, clear.
  - Companion protocol v2: RGB strip frames `P<rrggbb...>`, matrix rows `Q<row>:...`, gauge `G`, 7-seg `7`, buzzer `Z`, brightness `Y`, and capability query `?`.
  - Capability response format: `K:<key>=<detail>` and `KEND`.
- `firmware/companion-iflag/companion_iflag.ino`
  - Working 8x8 WS2812/WS2812B RGB matrix firmware.
  - Supports `?` capability query and replies `K:rgbMatrix=8x8`, `KEND`.
  - Supports `Q<row>:<8*rrggbb>`, `P<rrggbb...>`, `Y<brightness>`, and `C`.
- `src/main/modules/device-config.ts`
  - Persists Hardware Hub profiles and exposes test output per component.
- `src/main/modules/device-output.ts`
  - Drives generic companion devices from telemetry and component config.
- `src/renderer/src/views/HardwareHubView.tsx`
  - Existing UI for devices/components, board choice, serial link, pin conflicts, and component testing.

### Product principle

SimHub asks: "Which sketch options do you want?"

Our app should ask: **"What hardware did you buy, and what do you want it to do?"**

Firmware selection should become an implementation detail.

### Proposed UX: module-first wizard

Add a **Setup hardware** / **Add module** flow inside Hardware Hub:

1. **Choose what you connected**
   - Cards: iFlag 8x8 RGB Matrix, WS2812 Rev Lights, SSD1306 OLED, TM1638, TM1637, MAX7219 7-seg, Buttons, Encoders, Button Matrix, Servo Gauge, Buzzer.
   - Each card shows photo/icon, difficulty, board compatibility, required parts, power warning, and "works best with" board.
2. **Choose board**
   - Recommend board automatically from module:
     - iFlag 8x8 -> Nano/Uno first, ESP32 for larger matrices.
     - HID controls -> Pro Micro/Leonardo.
     - OLED + several modules -> Mega.
3. **Show wiring**
   - Display exact pins and alternatives.
   - Highlight pin conflicts live using existing `DeviceProfile.components[].pins` model.
   - Default iFlag MVP: `D6`, serpentine `true`, orientation `0`, brightness `120`.
4. **Pick firmware**
   - Default: "Recommended prebuilt firmware".
   - Advanced: "Customize pins / compile with arduino-cli".
5. **Flash**
   - Detect ports and board candidates.
   - Show the exact command in an expandable details panel.
   - Upload with retry logic and board-specific help.
6. **Verify**
   - Reopen serial at `115200`.
   - Send `?`.
   - Collect `K:` lines until `KEND`.
   - Match capabilities to component catalog.
7. **Create/update Hardware Hub profile**
   - Auto-create profile linked to serial device and board.
   - Add matching component(s) with detected details.
   - Run a self-test automatically: matrix rainbow, strip chase, OLED `TEST OK`, 7-seg `8888`, buzzer chirp.
8. **Make it useful immediately**
   - For iFlag: enable default flags/gear/spotter profile.
   - For rev lights: enable RPM gradient + shift flash.
   - For OLED: enable a default telemetry page.
   - For controls: open mapping assistant.

### Capability auto-detect contract

Use the existing companion v2 handshake as the backbone:

```text
App -> device:
?

Device -> app:
K:protocol=2
K:board=nano
K:firmware=iflag-ws2812-8x8@1.0.0
K:rgbMatrix=8x8;chip=ws2812;pin=D6;serpentine=1;orientation=0
K:brightness=0-255
KEND
```

Recommended standard keys:

| Key | Detail examples | Maps to |
|---|---|---|
| `protocol` | `2` | Companion protocol compatibility |
| `board` | `nano`, `uno`, `pro-micro`, `esp32` | `DeviceProfile.board` |
| `firmware` | `iflag-ws2812-8x8@1.0.0` | Profile metadata / update checks |
| `rgbMatrix` | `8x8;chip=ws2812;pin=D6;serpentine=1;orientation=0` | `RgbMatrixComponent` |
| `rgbStrip` | `16;chip=ws2812;pin=D6;colorOrder=GRB` | `RgbStripComponent` |
| `screen` | `ssd1306;128x64;i2c=0x3c` | `ScreenComponent` |
| `segDisplay` | `tm1638;digits=8;buttons=8;leds=16` | `SegDisplayComponent` + optional controls |
| `control` | `buttons=16;encoders=4;analogs=2;hid=1` | `ControlComponent` |
| `gauge` | `servo;count=1;pin=D9` | `GaugeComponent` |
| `buzzer` | `pin=D5;activeHigh=1` | `BuzzerComponent` |

This is better than SimHub because the app verifies the flashed firmware instead of trusting that the user's setup profile matches the physical board.

Use a manifest-driven firmware catalog:

```json

      },

      "defaults": {

        "serpentine": true,
        "brightness": 120
      }
    }

```

### Flashing service design

Add a main-process service later (not in this doc task) with this shape:

```ts
interface FirmwareTarget {
  firmwareId: string
  board: BoardId
  port: string
  artifactPath: string
}

interface FlashProgress {
  phase: 'prepare' | 'reset' | 'upload' | 'verify' | 'capabilities' | 'done' | 'error'
  message: string
  percent?: number
}
```

Responsibilities:

- Resolve firmware manifest entry.
- Validate artifact exists and checksum matches manifest.
- Close any open `SerialDevice` for the target port before flashing.
- For Uno/Nano/Mega: spawn bundled `avrdude` with safe arguments array, never shell-concatenated strings.
- For Leonardo/Pro Micro: perform 1200 bps touch, detect the transient bootloader port, then run `avrdude -c avr109`.
- For ESP: call bundled `esptool` or esptool-js with explicit offsets.
- Stream progress into renderer.
- Reconnect at `COMPANION_BAUD` and run `?` verification.
- Persist/update Hardware Hub profile only after capability verification succeeds.

### Why this beats SimHub

| SimHub | Our app should do better |
|---|---|
| User enables sketch options in a technical setup tool | User chooses a photographed module from a catalog |
| Pin conflicts are mostly warnings inside the setup form | Pin conflicts are prevented visually before flashing |
| Upload success does not necessarily prove the right module is present | Post-flash `? -> K:` handshake verifies capabilities |
| Multi-USB requires scan/order/apply mental model | Each serial device becomes an explicit Hardware Hub profile |
| Generated sketch can be overwritten by updates | Prebuilt versioned firmware with manifest/checksum/update path |
| Advanced users can customize, but beginners face many options | Beginner path is one-click; advanced path is opt-in |
| Module editors are scattered | Hardware Hub owns setup, test, flash, detect, and link |

## 6. Prioritized build plan

### Phase 0 — Ship the iFlag happy path

Goal: **pick 8x8 -> flash -> works**.

1. Add a firmware manifest for existing prebuilt iFlag artifacts:
   - `iflag-nano`
   - `iflag-uno`
   - `iflag-micro`
2. Bundle/find `avrdude` for Windows builds.
3. Add Hardware Hub action: **Flash firmware** on `rgbMatrix` components.
4. Implement board-specific AVR upload:
   - Uno/Nano: `avrdude -c arduino -p atmega328p -P <port> -b 115200 -U flash:w:<hex>:i`.
   - Pro Micro/Leonardo: 1200 bps touch + `avr109` upload.
5. After upload, reconnect at `115200`, send `?`, parse `K:rgbMatrix=8x8` + `KEND`.
6. Auto-create/update profile:
   - Board, port, baud `115200`.
   - Component: `rgbMatrix`, `chip=ws2812`, `width=8`, `height=8`, `serpentine=true`, `orientation=0`, `mode=iflag`.
7. Run test animation using existing `formatMatrixRowRgb`/`formatBrightness`.
8. Enable default iFlag renderer profile: gear + flags + spotter.

Acceptance criteria:

- A user with a Nano + WS2812B 8x8 can start from no profile and end with a working matrix without editing pins or source.
- Failed upload explains the likely issue: wrong port, old Nano bootloader, CH340 driver, board not in bootloader, cable/power.
- Successful flash is not considered complete until `K:rgbMatrix=8x8` is detected.

### Phase 1 — Make it feel better than SimHub

1. Add catalog cards with wiring diagrams/inline instructions.
2. Add automatic port refresh and board guess from USB VID/PID/manufacturer string.
3. Add "Try old Nano bootloader" fallback at `57600`.
4. Add firmware version detection and update prompt:
   - `K:firmware=iflag-ws2812-8x8@x.y.z`.
5. Add persistent flash logs for support.
6. Add post-flash test patterns:
   - Rainbow fill.
   - Row/column orientation test.
   - Serpentine correction prompt: "Does the arrow look correct?".

### Phase 2 — Add high-value modules

1. WS2812 rev lights firmware:
   - `K:rgbStrip=<count>;pin=D6;colorOrder=GRB`.
   - Reuse app's `stripColors()` engine and `P` frames.
2. SSD1306 OLED firmware:
   - `K:screen=ssd1306;128x64;i2c=0x3c`.
   - Reuse existing OLED page model and `T`/`N` frames.
3. Pro Micro controls firmware:
   - `K:control=buttons=...;encoders=...;analogs=...;hid=1`.
   - Integrate with input monitor and mapping assistant.

### Phase 3 — Segment displays and combined modules

1. TM1637 4/6 digit.
2. MAX7219 7-seg.
3. TM1638 combined display/buttons/LEDs.
4. MAX7219 mono matrix compatibility.

### Phase 4 — Advanced outputs

1. Buzzer alert firmware.
2. Servo gauge firmware.
3. Stepper/automotive gauge firmware with calibration wizard.
4. ESP32/ESP8266 flashing support with esptool.
5. ShakeIt-style motors/wind only after core Hardware Hub firmware lifecycle is solid.

## 7. Implementation guardrails

- Do not require Arduino IDE on the user's PC for the beginner path.
- Do not make users copy/paste commands.
- Do not mark flashing successful until capability verification passes.
- Do not let source-code generation be the primary beginner path; prebuilt artifacts should cover common modules.
- Do not hide power warnings for LEDs, motors, fans, or 12V gauges.
- Do not auto-flash the primary SIM-X device unless the user explicitly picks it; Hardware Hub currently skips SIM-X for generic output, and the flashing flow should be equally conservative.
- Always close serial handles before invoking upload tools.
- Spawn upload tools with argument arrays; never shell-concatenate user-controlled paths/ports.
- Store firmware metadata and logs so support can diagnose exactly what was flashed.

## 8. First implementation recommendation

Build only one vertical slice first:

> **Hardware Hub -> Add module -> RGB Matrix / iFlag 8x8 -> Arduino Nano/Uno/Pro Micro -> Flash recommended firmware -> Verify `K:rgbMatrix=8x8` -> Auto-create profile -> Run rainbow test -> Start telemetry output.**

This is the smallest slice that proves the entire product promise. Once this works, every later module is mainly catalog metadata, firmware artifact, flasher adapter, and capability-to-profile mapping.
